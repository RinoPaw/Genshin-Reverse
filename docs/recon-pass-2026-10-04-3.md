# Reconnaissance pass 3 — 2026-10-04

This pass focused on current 7.1 server/protocol repositories, historical Quest conversion, exact-client BinConfig extraction and version-resilient native anchors.

It records method leads and confidence boundaries. Nothing here promotes a third-party semantic mapping into the Global 7.1 canonical dataset.

## 3. Quest conversion has historically mixed extraction with compatibility repair

Historical `233-Jerry/Grasscutter-Resources` tooling makes the failure mode concrete. `Tool/MergeQuests.js` did more than serialize existing Quest data:

- it mixed older QuestExcel rows, newer BinOutput and manual patches;
- it inserted an artificial `QUEST_COND_UNKNOWN` for some new quests;
- it coerced object-valued condition combiners to `LOGIC_NONE` while marking the operation uncertain;
- it normalized/null-filled fields during the same pass.

`QuestGC.js` similarly mixed multiple historical Excel versions with BinOutput-derived rows.

These scripts are not the current AnimeGameData pipeline. Their value is methodological: a published `QuestExcelConfigData.json` can look structurally clean while containing compatibility transforms that were never present in the client serialization.

This directly motivated issue #8 and `methods/binconfig-extraction-validation.md`.

## 4. Exact-client BinConfig extraction gives us a stronger root-cause method

`owomocha/genshin-7.0-local-re-devkit` publishes a modern exact-build workflow for Genshin BinConfig/Excel tables. The important method is broader than its 7.0 target:

1. locate `Data/_ExcelBinOutput/*` / `Data/_BinOutput/*` literals in the executable;
2. use IL2CPP signatures/native xrefs to identify the owning loader and row deserializer;
3. reconstruct the row schema from the exact deserializer rather than from expected JSON;
4. locate candidate serialized table blobs;
5. accept a candidate only when the decoder consumes the full payload exactly;
6. if a schema is slightly wrong, search constrained structural mutations and accept only variants that satisfy the same byte-consumption invariant.

This is a much stronger way to answer the Quest question than comparing two generated JSON repositories.

For 7.1 Global we should independently implement the method against the pinned sample rather than importing another project's code or target constants.

## 5. Traffic-derived protobuf facts have an asymmetric evidence rule

The same 7.0 toolkit uses decrypted traffic to supplement static schemas and states an important rule explicitly: observing a field/wire pair proves that the path exists; failing to observe it does not prove that the field does not exist.

This belongs in our own protocol evidence discipline. Sparse runtime captures must not be converted into negative schema claims.

Its unknown-command workflow is also useful as a checklist: registry/type identity + field number/type/object offset + typed handler signatures + handler disassembly/callees + string literals + runtime wire shapes. That is close to the direction our `protocol-query` aggregator is already taking.

## 6. Old “Genshin KCP” claims are not transport proof for a modern build

`nonobject14514/kcp-genshin` advertises broad Genshin compatibility, but its published source still exposes a 28-byte KCP overhead and the included protocol text describes the classic 24-byte layout.

A modern exact-build investigation for 7.0 instead measured a 32-byte segment header with an extra 32-bit checksum word derived from XXH3 and validated it against captured traffic/tests.

The lesson is not which historical repository was “wrong” for its own era. The lesson is that README claims such as “works with every version” do not establish a transport format for our exact target. Transport/framing must be sample-bound just like CmdIds and metadata offsets.

No new transport issue is opened because current AstaPS/Genshin-Reverse work is not blocked on this layer.

## 7. Version-resilient native anchors: mask relocations, keep fallbacks, cross-check implementations

A current Android 7.0.1/7.1.0 reverse/patch project (`GenshinPlusPlus`) documents a useful native-anchor discipline:

- rediscover locations by byte signature rather than hard-coded offsets;
- mask relocation/address-sensitive bytes such as `adrp` immediates and changing structure offsets;
- keep fallback signatures for the same logical anchor;
- verify signatures against multiple real builds;
- run two independent scanner implementations and require them to resolve the same offsets;
- regression-test masked matching, fallbacks and idempotency.

The concrete patch target is unrelated to our Windows protocol work, but the method is relevant to future `NativeProfile` bring-up. Automatic discovery should propose anchors; publication should still bind the accepted result to exact hashes and sanity checks.

This is a method lead, not a reason to weaken fail-closed profiles.

## 8. Protocol translation exposes a family-completeness failure mode

`ViaGenshin` translates between protocol versions and documents a practical failure mode: Ability/Combat can fail when protobuf definitions are incomplete, especially the interconnected `AbilityMeta*`, `AbilityMixin*` and `Evt*` families.

For #7 this suggests an additional acceptance dimension beyond individual message shape recovery: report whether referenced protocol families close transitively. A message that parses alone may still be unusable if nested/oneof/referenced types are missing or structurally wrong.

Do not infer current field numbers from ViaGenshin mappings. Use the project as architecture/failure-mode evidence only.

## 9. Barbara C6: local-id filtering got stronger, argument inference got weaker

`invoker-bot/LunaGC` commit `1b363fac36d218ecfce3452a3c1893fe0fac6b31` gives a useful same-version CN cross-check for issue #4.

Its Barbara revival test executes the actual `Avatar_Barbara_ReBorn` resource and selects the third `onAbilityStart` action (`onAbilityStart[2]`) as `ReviveAvatar`. Its deterministic action local-id generator uses:

```text
1 + (configIndex << 3) + (actionIndex << 9)
```

with `onAbilityStart` at config index 2 and the third action receiving action index 3. That yields candidate local id `1553`.

This is a search filter, not live-client proof. More importantly, the server's `onAbilityInvoke()` routes every entry with a non-zero `head.local_id` into local action/mixin lookup **before** its `argument_type` switch. The 7.1 enum also has no dedicated `REVIVE_AVATAR` invoke argument. Therefore the server implementation cannot establish Barbara's concrete live `argument_type` or `ability_data`.

Issue #4 now records both boundaries: prioritize `local_id == 1553` during exact-Global CmdId 6622 capture, but recover the argument enum and payload independently.

## 10. Artifact Excel `weight` names are a rejected shortcut, not proof of field absence

Resource history narrows issue #5.

Historical 4.0 `ReliquaryMainPropExcelConfigData` exposes a `weight` field, but it is `999` across very different main-stat types. That cannot encode the familiar non-uniform sands/goblet/circlet stat-selection distribution. Historical `ReliquaryAffixExcelConfigData` likewise uses broadly uniform `weight = 150` and `upgradeWeight = 1000` across stat classes and roll tiers, so those fields do not directly encode the desired substat-class distribution either.

Current 7.1 public resource output omits those fields. However, Dimbreath documented a major extraction boundary from 5.5 onward: new encryption plus a field-order shuffle severely damaged deobfuscation. Therefore absence from current published JSON is **not** proof that the serialized client row lacks an analogous field.

The correct split is:

- REJECTED: historically named `Reliquary*.weight` fields directly equal the artifact probability table we want;
- UNRESOLVED: whether current 7.1 still contains hidden/obfuscated fields at the serialized-row level;
- UNRESOLVED: whether the authoritative probability model lives in another table/native path or is server-only.

This makes an exact-client schema/consumer recovery more valuable than searching additional JSON mirrors.

## 11. A second current resource dump exists, but its extraction lineage is not yet proven independent

`GuraFoundation/YuanShenResources` is actively publishing current/beta resource output, including recent `CNCBWin7.1.50` Excel/BinOutput commits. Some rows retain unknown obfuscated field names, which is useful as a reminder that current dumps are incomplete semantic projections rather than pristine source schemas.

At present the public repository exposes data but not enough extractor/toolchain provenance to prove that its Quest/Excel output is independent of the Dimbreath/AnimeGameData extraction lineage. Treat it as a candidate cross-check source, not an independent extraction edge, until that lineage is established.

For #8, a genuinely useful second source would need either its own documented decoder/schema recovery or an exact-client direct decode that can be compared without sharing the same transformation chain.
