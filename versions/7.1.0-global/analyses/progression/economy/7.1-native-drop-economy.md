For the highest native reward range, a raw 1 -> 90 requirement of 8,362,650 EXP implies a hard best/worst reward-range bound of:

- **62 runs** if every run yields 135,000 EXP;
- **77 runs** if every run yields 110,000 EXP.

The current 7.1 DropTable rows use `randomType = 1` and weight 10000 for each listed EXP component. A matching Grasscutter `DropSystem.calculateDropAmount` implementation treats `a;b` as a uniformly sampled inclusive integer range and evaluates all randomType-1 entries independently. This runtime interpretation is evidence `B`.

For the highest tier, that gives four equally likely raw EXP outcomes per base claim: **110k / 115k / 130k / 135k**, with mean **122,500 EXP**.

- Ratio-equivalent requirement: 8,362,650 / 122,500 = **68.27 claims**.
- Exact expected stopping time under the uniform-inclusive `B` semantics: **68.77 base claims** to reach or exceed the Lv.1 -> 90 EXP target.
- Expected Resin at 20 per claim: about **1,375 Original Resin**.

The hard reward-range bounds remain 62-77 claims, or **1,240-1,540 Original Resin**, before multi-claim/Condensed Resin rules.

## 7.1 talent-Domain source-to-drop-node linkage (2026-10-09)

The pinned `DungeonExcelConfigData` contains an obfuscated field
`IAOMJCLOIEL` in **all 104** talent Domain rows. Exact ID lookup into the
pinned `Server/DropTableExcelConfigData.id` succeeds for **56/104**;
48 IDs have no corresponding root row in this source table. Missing IDs are
concentrated in source `cityID` **5, 6, 7 and 8** (12 Domain rows each).
The missing roots are **not evidence of zero drops**. The data source is
incomplete for those cities; current yield calculations must remain blocked.

For the 56 linked roots, the full reachable drop-node graph contains
**112 DropTable nodes and 6 DropSubTable nodes**. Their terminal nodes resolve to **39 distinct DropMaterial item IDs**, all represented in the corresponding Dungeon reward previews. This material validation does not establish actual draw probabilities. The `itemId` on a
`dropVec` entry can reference another drop node, not necessarily an inventory
item. In particular, Dungeon **4200** points to root **82012700**, which
references node **82012711** and shared DropSubTable node **510000**; the
latter lists material IDs **104301, 104304, 104307**. The source preserves
`countRange`, `weight` and `randomType` as raw values; strings like
`"2.2"` are **not yet interpreted as either literal awarded counts or
probabilities** without a current drop-system consumer. Even a complete
root graph does not prove the client/server chooses that root at claim time.

Reproducible evidence: [talent Domain drop links](7.1-talent-domain-drop-links.json),
generated by `scripts/collect-7.1-talent-domain-drops.py` from exact
`RinoPaw/AstaPS-Resource@b0f3a2791607cab2a4c24cb9ef249dd2d94d7ffd`
blobs. The collector rejects changed source blobs.

### Consumer comparison and remaining gate

`RinoPaw/AstaPS` DropSystem blob
`e8269faca8b46a771f2214242edceaee0f35abb2` provides an implementation
comparison: decimal count strings use stochastic rounding (`2.2` becomes 2
or 3 with the fractional part used as the chance of the additional unit);
semicolon ranges use inclusive integer sampling. Random type 0 chooses one
weighted entry; type 1 tests each entry against a 10,000 denominator.
This is **B implementation evidence**, not a confirmed original 7.1
probability model. Its processDrop also ignores fields such as dropLevel and
daily limits, and the editable DomainStatueDropService path can take precedence.
Do not publish final native farming counts by running this comparison model
against a graph whose claim-time selection and terminal identities are unbound.

Next gates: recover missing source roots; bind claim-time root selection and
nested-node handling; bind actual item identities; trace the separate Boss
