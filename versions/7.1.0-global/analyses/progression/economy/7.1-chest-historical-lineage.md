The earlier file was committed in April 2024. Its six columns (`最小等级`, `总索引`, `掉落ID`, `掉落次数`, `产出来源类型`, `类别`) correspond to `minLevel`, `index`, `dropId`, `dropCount`, `sourceType`, `type`. A field-by-field **multiset** comparison preserves duplicate counts and detects replacement rows:

| --- | ---: |
| 2.8-labelled historical TSV | **980** |
| AstaPS server JSON | **1,771** |
| Six-field identical historical rows | **980** |
| Historical rows absent or modified | **0** |
| Extra AstaPS records | **791** |

The earlier file already contains `战斗低级蒙德` and `解谜低级蒙德` with level-one roots `51010000` and `52010000`; `TagArrangeLimit.txt` separately uses the same tag strings. Their only known origin is therefore **not** the later Chiori/Grasscutter mapping. However, neither this historical publisher nor its copy documents an authenticated original MiHoYo server extraction. Identical content might share another ancestor. The 791 added rows span more than ordinary chests and cannot be called native 7.1.

**Never infer 7.1 authority from old records.** The source word `低级` describes a historical configured chest grade; it does not by itself describe low-Primogem geography. `Server/DropTableExcelConfigData.json` has independently documented 6.5-era provenance, and its weights remain unverified for the current 7.1 server.

## Read-only reproduction

From Genshin-Reverse, with neighbouring historical and AstaPS checkouts pinned to the revisions above:

```sh
python scripts/audit-chest-drop-ancestry.py \
  --historical ../2.8_live_data/txt/ChestDropData.txt \
  --server ../AstaPS/data/ChestDrop.json \
  --historical-blob b77c3e486982d654964d4b4103df7ae59362a0dc \
  --server-blob 789e885d37535280dc923e5c69e1aa2fc23714dd \
  --check-contained
python -m unittest tests.test_chest_drop_ancestry -v
```

The audit requires the exact source file format, checks optional Git blob guards and reports missing, changed and added records without rewriting inputs. A reproducible Git blob fingerprint validates **identity of a public copy**, not the game's original authorship.

## Native 7.1 promotion gates

1. **Object identity:** recover Gadget config asset and schema/load path from the pinned **Global 7.1** client. Cross-check against the already-maintained independent CN 7.1 GadgetExcel comparison in [the chest reward study](7.1-chest-reward-evidence.md); do not mistake agreement of 309 `Chest` rows for verified native original bytes.
2. **Instance authenticity:** find an exact source for each scene/group/config. Determine whether the client even ships `Scripts/Scene`/`drop_tag`; these may be server-only and unavailable from the client executable. Distinguish missing evidence from absence in the game.
3. **Reward ownership:** verify whether any client- or server-authored `chest_drop_id` references a nonempty payable root. Special/quest/remarkable chests, sentinel roots and tagless instances remain separately unresolved until proven.
4. **Probability:** require authenticated 7.1 server source/consumer or appropriately controlled official-server observations before accepting exact default item weights. Historical config/derived classes/custom rules must retain their own status.

The current AstaPS Loot branch uses `ChestTypeResolver.fromExploreKind("chest_puzzle") -> normal`, grade heuristics in `WorldChestLootHelper.resolveTier()`, and geography/default distributions in `chests.css`. These are implementation policy. A tag derived from an imported marker is **not** a recovered original scene field. Keep Loot parsing and claim validation separate from reward authenticity.
