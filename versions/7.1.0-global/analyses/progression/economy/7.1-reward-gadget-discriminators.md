# 原神 7.1：奖励 Gadget 的识别属性清单

更新：2026-10-21。对应 [#31](https://github.com/RinoPaw/Genshin-Reverse/issues/31)。

## 任务范围

**只研究如何辨认奖励 Gadget 及其对应的实例。物品、奖励数量、掉落概率由服主自行配置，本研究不验证、不迁移、不推荐任何掉落数值。**

区分三种来源，禁止互相冒充：

1. **原版 Global 7.1 客户端**：从有 SHA-256 来源的 Sophon 原始 `GadgetExcelConfigData` 完整解析出的 **30,599** 行，其中原生类型码候选 `26` 的 **309** 行。能证明 Gadget 的 ID、原生名字、部分原生字段和字段出现情况。原始 SHA-256 `a35e3f3ed04f950cb6302099d12aa71e23ece21d8fe578950347d9318f769e35`，参见 [原始控制数据](7.1-chest-native-gadget-prefab-controls.json)。
2. **历史 Lua 场景副本**：`MeChen618/AstaPS-Resource@85b81a69`，通过 [已固定哈希的历史扫描](https://github.com/RinoPaw/Genshin-Reverse/actions/runs/38499376170) 读取 14,084 个候选。能观察实例中有哪些字段及其组合，**尚不能证明它们就是 Global 7.1 场景**。
3. **AstaPS 实现与自定义导入层**：`RinoPaw/AstaPS@49e2183` 的 `feat/reward-language-core-71` 分支，可验证服务端当前是否能获取某属性；并不表示该属性由官方直接定义。

## 1. 原版 Gadget 定义里有哪些区分线索

| 属性 | 可确定的内容 | 限制 |
| --- | --- | --- |
| Gadget 原生 ID | 原始定义行的 uint32 键；全部 30,599 行完整解码 | 运行时包装器还进行 ID 字节代换；跨引用需核对 |
| 原生对象名称 | `SceneObj_Chest_Default_Lv3`、`SceneObj_Chest_Relic`、`SearchPoint` 等精确字符串 | 名称包含 `Lv` 也无法证明奖励档次 |
| 原生类型码候选 | 309 条记录的某原生字段值为 `26`；其中 162 个 `SceneObj_Chest` 前缀、21 个 `SearchPoint` 前缀，另有 126 个其他名称 | 类型码 26 包括宝箱以外对象；它不能单独判定“普通宝箱” |
| 外观/配置字段 | 原始图标字符串、存在性标志、布尔位、部分整数和列表字段 | 未确认含义的字段保持原生名字/偏移，不能凭猜测命名 |
| 核心宝箱前缀与后缀 | `Default/Locked/Bramble/Frozen × Lv1..Lv5` 的 20 种确实存在，含全部四个 `Lv3` ID | 五种原生后缀与通常所说四档宝箱品质尚无已验证的对应关系 |

特别需要注意：`SceneObj_Chest_Relic`、其他特殊宝箱前缀值得单独建立候选组；当前未证明某个名字前缀一定对应“奇馈”或“地灵龛”，所以不直接给这些名字设置自创的奖励类型。

## 2. 场景里的每个具体 Gadget 有哪些属性

| 属性来源 | 具体字段 | 能区分什么 |
| --- | --- | --- |
| 场景与实体 | `sceneId`、`groupId`、`config_id` | 同地图、同组中具体哪个对象。静态场景优先用三元组 `scene/group/config` 标识 |
| Gadget 定义 | `gadget_id`、原生 `jsonName`、类型码 | 物件外形/功能定义；一个 ID 可以被很多不同实例重用 |
| Lua 对象参数 | `level`、`area_id`、`pos`、`rot`、`state` | 对象等级、位置、区域、状态；等级应读取实际实例字段 |
| Lua 类型线索 | `drop_tag`、`chest_drop_id`、`drop_id`、`drop_count` | 历史作者为该实例提供的识别标签或根 ID。只研究**字段来源与取值**，不推导奖励内容 |
| 存在周期 | `isOneoff`、`persistent`、`explore`、`trigger_count` | 一次性、持久化、探索对象、触发条件的线索；单独使用会误判 |
| 专用字段 | `point_type`、`interact_id`、`draft_id`、`route_id`、`owner` | 采集点、交互、玩法系统、路线及对象归属的进一步标识 |
| Boss 专用嵌套 | `boss_chest.monster_config_id`、`resin`、`life_time`、`take_num` | 用于区分世界 Boss 领取花、绑定怪物与实例生命周期 |
| 运行时来源 | `EntityGadget.content` 类别、`SceneType`、地脉 BlossomManager 是否认领 | 当前是普通宝箱、Boss 花、地脉花、副本奖励树还是采集 Gadget 的关键分流 |
| 地域派生 | `city`、父 `area`（由地图区域与场景资料解析） | 地区选择器；要注明它是查表/计算结果，场景原生 `area_id` 是另一字段 |
| 外部导入标注 | `SceneGadget.chestType`、`chestGrade`、`rewardRegion` | AstaPS/探索点导入补充信息，**这些不是已验证的原版 7.1 资产字段** |

历史 Lua 的 `level` 确实可能单独写在 Gadget 上。例如旧 `scene3_group133003154.lua` 中，Gadget `70211001` 同时有 `level=1` 与 `drop_tag="战斗低级蒙德"`。然而上一轮保存的 14,084 条场景 CSV **遗漏了 `level` 一列**，不能由那份 CSV 再算出每个对象的真实等级。字段缺失或默认 0 要与显式 `level=0` 区分。

## 3. 奖励 Gadget 类别与优先使用的识别字段

| 对象 | 优先识别依据 | 暂不能当作唯一依据的字段 |
| --- | --- | --- |
| 普通世界宝箱 | Gadget 原生 ID/名字 + 实例标识 + 已知胸类型来源；若有实际来源的 `chestGrade` 再识别品级 | 单凭 `_Lv3`、音频 `Mid`、原生类型码 26、中文 `高级` |
| 战斗/解谜宝箱 | 实例 `drop_tag` 原样标签或明确的机制来源，连同 Gadget、区域与实际等级 | 同一个 `gadget_id` 可能出现在多个标签与等级下 |
| 搜刮点/调查点 | `SearchPoint` 名称线索 + `point_type`、历史 `搜刮点*` 标签、一次性/探索标志 | `type=Chest` 候选、`gadget_id=70210101` |
| 摩拉石箱 | 历史 `摩拉石箱*` 标签或可信导入 `chest_mora` 标记 | 名字 `Chest` 或 Gadget ID；共享定义的可能性存在 |
| 奇馈宝箱 | 有来源的 `chest_remarkable` 导入标记，待追溯原版专用对象特征 | 仅以 `Relic` 字样推断奇馈 |
| 地灵龛、任务宝箱、活动宝箱 | 实例 `drop_tag`/特殊事件来源、`group/config`、解锁/任务上下文 | 普通四档 `grade`；某些 Gadget ID 被复用 |
| 世界 Boss 领取花 | `boss_chest` 嵌套是否存在、关联 `monster_config_id`、`scene/group/config`、运行时内容对象 | 名字有 `Chest`，或 `drop_tag` 恰好是怪物名 |
| 地脉奖励花 | 地脉管理器确实认领当前实体，再按管理器的藏金/启示上下文区分 | `GadgetChest` 类别或单个 Gadget ID |
| 副本奖励树 | `GadgetRewardStatue` 内容对象、当前副本上下文及专用 Gadget ID | 与世界 Boss 领取花混为同一类 `chest` |
| 采集/矿物 Gadget | `GadgetGatherPoint/GadgetGatherObject` 内容对象、`point_type`、采集数据 | 根据是否掉出物品就把它归为宝箱 |

来源分流**先识别奖励事件/交互对象类型，再检查实例字段**。如果一个实例缺少必要的属性，保留“未识别”，不要默认为普通宝箱。

## 4. 历史数据证明 ID 和奖励类型无法一一对应

从固定的历史 CSV 重新计算，共有 **171 个不同 Gadget ID**；其中 **37 个 ID** 曾以两种或三种元数据来源出现，**21 个 ID** 同时出现 `drop_tag`、`chest_drop_id` 和两者缺失这三种情况；**28 个 ID** 具有多个不同 `drop_tag`，其中 `70210101` 有 **33** 种。

三个典型例子：

| Gadget ID | `drop_tag` | 明确根 ID | 都没有 | 区分问题 |
| --- | ---: | ---: | ---: | --- |
| `70210101` | 2,447 | 88 | 1,388 | 多种搜刮点标签、同 ID 的无奖励字段实例 |
| `70211101` | 1,455 | 51 | 90 | 常见解谜用途，也可带不同地区/品级文字 |
| `70211001` | 498 | 26 | 54 | 常见战斗用途，各地区标签、任务实例混用 |

因此，`gadget=70211101` 只能识别某个物件定义，不能自动说明它的地区、奖励类型或领取条件。这些统计**仅属于历史 Lua 副本**。客户端原版 7.1 的 20 个核心定义 ID 在此历史扫描中一个也没有出现，进一步说明二者不能不经核验就互相代替。

复现：`scripts/audit-7.1-reward-gadget-discriminators.py`；测试 `tests/test_reward_gadget_discriminators_71.py`；[机器可读属性清单](7.1-reward-gadget-discriminator-inventory.json)。

## 5. 当前 LootCSS 的属性可用性（奖励分支）

从 `feat/reward-language-core-71@49e2183` 读取：

- `RewardCssAttributes` 声明整数型 `city, area, WR, level, scene, point, gadget, group, config, rank, world_level, wl, tier, power`，字符串型 `type, grade, tag, mode, kind`。
- **但“声明了”不等于已经从 Gadget 填入。** `WorldChestLootHelper.grant` 在普通宝箱上下文实际上提供：`type`；仅 `normal` 才有的 `grade`；`scene`、`gadget`、`group`、`config`；有 `meta` 时提供 `level`；以及成功解析地区时的 `area`、`city`。
- 对 **普通世界宝箱**，`tag`、`kind`、`point`、`WR`、`world_level` 等虽然在类型表声明，目前**没有在上述胸部上下文填入**，不能把 `chest[tag="..."]` 当作已能使用的过滤条件。
- `ChestTypeResolver` 有 `normal/mora/remarkable`，其中 `chest_mora`、`chest_remarkable`、`chest_puzzle` 等来自**导入点类别**；`chest_puzzle` 被映射到 `type="normal"`，不会自动提供 `grade`。`chestGrade` 是附加来源属性；缺失时 `WorldChestLootHelper.resolveTier` 还会从 ID 和 `jsonName` **推测**品级。
- 当前世界 Boss 使用 `SceneGadget.boss_chest`、`monster_config_id`、`group`、`drop_tag` 等独立依据；地脉和副本奖励树还需要各自管理器/副本上下文，不能因为继承同一 GadgetContent 体系而继承宝箱的选择器属性。

**待办只剩属性证据**：恢复来源可信的 Global 7.1 场景 `scene/group/config`；进一步核实独立于 Lua 标签的原版交互/用途字段；逐个查清 Mora、奇馈、地灵龛、世界 Boss、地脉花与副本奖励树的原生身份与可用上下文。无需寻找、核对或修改任何奖励数量及掉率。
