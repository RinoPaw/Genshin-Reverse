# 7.1 宝箱研究：历史场景来源与当前 AstaPS 发奖链路的断点

研究日期：2026-10-21。追踪：[Issue #31](https://github.com/RinoPaw/Genshin-Reverse/issues/31)。

**结论：在当前 AstaPS 中，普通宝箱的 `drop_tag` 不直接进入 `ChestDrop.json` 的标签查表方法；大多数普通开箱会走一套 Gadget 名称/中文标签推测品质的固定奖励逻辑。这里存在明确的实现断点。以下统计只描述历史社区场景数据，尚不能证明原版 7.1 的奖励规则。**

## 1. 输入来源和统计口径

历史场景来自 [Actions #38499376170](https://github.com/RinoPaw/Genshin-Reverse/actions/runs/38499376170) 保留的完整 `chest-region-71-audit` 产物：扫描 `41,110` 个 Lua 场景文件，收录 `14,084` 条根据**社区 GadgetExcel `Chest` 类型**筛出的候选记录，另排除 `43` 条 `boss_chest`。`chest-region-per-gadget.csv` SHA-256 为 `ba53152e17dbe019482920ad179ff90c62419d385390f9d0eb952dcb7895dcc1`；`chest-region-summary.json` 为 `c2e81ab79eb891f448421a6944017c0d1ccc3547079fa1364dae8bde0a117d58`。来源锁定 `MeChen618/AstaPS-Resource@85b81a69`、扫描器 `RinoPaw/AstaPS@e2541630`，**不具备原版 Global 7.1 客户端场景资产认证**。

| 历史候选记录的掉落元数据 | 全场景数量 | 占全部候选 | scene 3 数量 | 额外说明 |
| --- | ---: | ---: | ---: | --- |
| 只有 `drop_tag` | **9,020** | **64.04%** | 7,130 | 109 种不同的中文标签 |
| 只有 `chest_drop_id`（正整数） | **1,339** | **9.51%** | 980 | 413 种不同的数字根 ID |
| 两者都没有 | **3,725** | **26.45%** | 3,636 | 这 3,725 条 `is_oneoff=False` 且 `explore_chest=False`，**不能据此认作普通可领奖宝箱** |
| 合计 | **14,084** | 100% | 11,746 | 三组在这份扫描产物中互斥 |

与普通宝箱有关的中文标签有 `战斗低级蒙德`、`解谜中级璃月`，也有 `摩拉石箱须弥`、`搜刮点解谜遗物须弥` 等。**这一列记录的是历史场景掉落标签，直接当四档宝箱品质会丢失来源/对象语义。**

## 2. 当前 AstaPS 的实际普通开箱路径

检查了 `RinoPaw/AstaPS@dcf04369a356486a07be976b244b83d7208c3992` 的以下 Java 源码，并锁定 Git blob，防止未来漂移：

- [`GadgetChest.java`](https://github.com/RinoPaw/AstaPS/blob/dcf04369a356486a07be976b244b83d7208c3992/src/main/java/emu/grasscutter/game/entity/gadget/GadgetChest.java)（blob `72293aed5983092fe0e27d992ba3c1ba08c5f4b7`），方法 `grantOrdinaryChestLoot`。
- [`DropSystem.java`](https://github.com/RinoPaw/AstaPS/blob/dcf04369a356486a07be976b244b83d7208c3992/src/main/java/emu/grasscutter/game/drop/DropSystem.java)（blob `e04918a478e75414435f89f8bfd002f39d804af3`），方法 `handleChestDrop`、`hasQuestItemDrop`。
- [`WorldChestLootHelper.java`](https://github.com/RinoPaw/AstaPS/blob/dcf04369a356486a07be976b244b83d7208c3992/src/main/java/emu/grasscutter/game/entity/gadget/chest/WorldChestLootHelper.java)（blob `395092db65f81407087f98275bb2b57bfc976517`），方法 `resolveTier`、`grant`。

**普通宝箱**的分支为：

1. `chest_drop_id > 0` 时，且场景是副本、`groupId==0`，或 `DropSystem.hasQuestItemDrop(chest_drop_id)` 成立，才尝试 `handleChestDrop(chest_drop_id, drop_count, gadget)`；如果该奖励根不存在或调用失败，继续进入回退。
2. 其他情况（包括仅有 `drop_tag` 的绝大多数历史候选）直接使用 `WorldChestLootHelper.grant`。它先根据 Gadget ID / `jsonName` 中的 `Lv` / `drop_tag` 的中文字眼推断四档，再发固定物品、摩拉、原石、地区印记。
3. `DropSystem` **确实定义了** `handleChestDrop(String dropTag, int level, GameEntity bornFrom)`，内部会查 `ChestDrop.json` 的标签→根映射；但普通宝箱的 `GadgetChest.grantOrdinaryChestLoot` **没有调用这个字符串版本**。这不能推导出此函数在其他调用者中无用。

现有 `WorldChestLootHelper.Tier` 中写死的原石数量分别为 **66 / 166 / 366 / 566**（普通/精致/珍贵/华丽），这只是当前私服代码中的具体数值，**没有任何原版 7.1 发奖权威来源支持**。另有冒险经验、摩拉、印记、矿石和经验书的固定数量，同样必须保持「私服回退值」的来源标识。

**明确边界**：不能据 980 条 scene 3 `explicit_id` 候选推断它们都能按 ID 领奖。普通世界场景仍需检查 ID 指向的掉落树是否含任务道具、根是否存在及实际执行条件。也不能把 9,020 条 `drop_tag` 候选直接认作确实在服务器中调用了标签掉落表。

## 3. 对下一步原版逆向的实际影响

原版 7.1 `GadgetExcelConfigData` 已能完整解码 **30,599** 行，它描述 Gadget 定义；原版的音频分类表 **56** 行也已完成字节解析。这两者都不提供官方服务器奖励根、按地区调整的数量或 `drop_tag` 权重。

后续优先验证：

1. **实际放置**：从有原始 SHA/版本链的 scene/group/config 数据恢复可领取的实体，按 `gadget_id` 区分普通、任务、搜刮、特殊宝箱。
2. **奖励入口**：核实原生 `chest_drop_id` / `drop_tag` 的来源权威和各自适用场景，尤其历史场景标签怎样对应权威服务器掉落树。
3. **支付规则**：找到原版 7.1 服务端奖励根及权重来源后，再决定 LootCSS 应使用哪些选择器。不得从音频标签、Gadget 名称后缀或上述四组硬编码数值推出官方掉落品质。

复现：`scripts/audit-chest-historical-claim-routing.py` 读取上面校验过的两份 Actions 产物和三份 Git-blob-pinned Java 源码，可复算记录分类及普通开箱分支。合成回归测试：`tests/test_chest_historical_claim_routing.py`。本研究**未修改 AstaPS 实现或奖励配置**。


## 4. 全部历史标签与旧掉落表的可复核关联（2026-10-21）

从**同一份哈希固定的 14,084 条历史场景扫描**重新筛出 9,020 条 `source=drop_tag`，得到 109 个不同标签。另读取 fork `RinoPaw/AstaPS@dcf04369a356486a07be976b244b83d7208c3992` 的 `data/ChestDrop.json`，Git blob `789e885d37535280dc923e5c69e1aa2fc23714dd`。该文件一共有 **1,771 行、215 个不同标签**。109 个场景标签全部精确匹配，不需要模糊字符串匹配或人为改写标签。

| 历史标签字面前缀分组 | 场景记录 | 不同标签 | 对应 `ChestDrop` 规则行 | 不同奖励根 |
| --- | ---: | ---: | ---: | ---: |
| 战斗、解谜、雪山战斗/解谜 | 5,252 | 46 | 156 | 92 |
| 搜刮点、水上搜刮点、一次性搜刮点 | 2,869 | 39 | 39 | 39 |
| 摩拉石箱 | 530 | 4 | 4 | 4 |
| 灵龛 | 38 | 4 | 4 | 4 |
| 书页 | 80 | 8 | 8 | 8 |
| 活动（逐月节、渊下宫） | 223 | 6 | 6 | 6 |
| 雪山玉髓 | 28 | 2 | 12 | 5 |
| **合计** | **9,020** | **109** | **229** | **158（去重）** |

其中 2,869 条搜刮点记录只涉及 5 种历史 Gadget ID，只有 **983** 条明确标为 `is_oneoff=True`，更不能全算普通宝箱。分组依据严格使用中文标签**开头的原始文字**；没有用音频 `Mid/Hi/Top` 或 `Lv` 后缀制造奖励等级。

例如 `战斗低级蒙德` 在 fork 的 `ChestDrop.json` 中有从等级 1 到 26 的 **6 个档位**，对应历史根 `51010000` 到 `51010500`；`搜刮点解谜通用须弥` 等标签只有 1 个档位。**原先的 14,084 条场景扫描 CSV 没有导出每个 Lua 对象的 level**，所以目前尚不能从那份统计为每个具体实例确定最终根 ID。也不能把 229 条选择规则误算成 229 种宝箱或 229 个独立根。

进一步校验 fork 同一 commit 的 `data/Server/DropTableExcelConfigData.json`，Git blob `ca9661f68b988c8b6cae0627dadab00fe9f2c860`：含 **16,895** 个唯一掉落节点。所有 **1,771** 条 ChestDrop 规则所引用的 **1,687 个不同根 ID 均存在**，每个根都有至少一条直接 `weight > 0` 的记录。上述 109 个场景标签关联的 **158 个根 ID** 自然也满足该条件。

这份检查只走了根节点的**第一层**，尚未递归验证子节点、引用是否循环、物品是否有效、数量怎样解释，以及是否实际发得出来。证明的是**fork 数据内部的名称和根 ID 对得上**，不能追认数据为原版 7.1，也无法改变前面发现的普通开箱调用链断点。

复现器：`scripts/audit-chest-historical-tag-selector-coverage.py`，输入 SHA-256 固定的历史场景 CSV、Git blob 固定的 `ChestDrop.json` 和可选的原样 `DropTableExcelConfigData.json`。对每个标签输出档位及直接根节点覆盖情况。合成测试：`tests/test_chest_historical_tag_selector_coverage.py`。

**后续还必须证明原版 7.1 的场景实例来源和服务器掉落表来源。暂不接线，不写入 AstaPS 奖励系统。**
