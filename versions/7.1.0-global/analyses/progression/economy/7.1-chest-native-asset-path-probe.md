## Candidate raw-export verification gate (2026-10-21)

The same read-only probe now optionally accepts --asset-export pointing at an exported
MiHoYoBinData directory from an exact-client block export, and --strict-exports.
Only HASH_RESOLVED candidates are eligible. It locates exportedName.dat,
checks the MiHoYoBinData length frame, records raw and unwrapped payload
SHA-256 plus group/block IDs, and flags missing or malformed exports explicitly.
A collision in the 8-character exported file stem is rejected instead of being
silently assigned to a candidate. No payload bytes or proprietary assets enter
the report, and nothing changes AstaPS rewards.

Example, executed from the Genshin-Reverse checkout:

    python scripts/probe-7.1-chest-native-assets.py --index-raw /path/to/7.1-design-index.raw --asset-export /path/to/extracted-block --strict-exports --output /tmp/7.1-chest-candidate-raw-manifest.json
    python -m unittest discover -s tests -p test_chest_native_asset_probe_71.py

The design-index digest is checked before scanning, with existing positive
Quest/Dungeon controls. The asset-export directory is **not independently
authenticated by that check**. Original 7.1 provenance needs pinned source
block bytes, block digest, exporter identity and derivation chain, followed by
a native row deserializer and full-byte-consumption validation. A raw hit is
still not evidence of chest drop roots, grades, random weights or any reward
ownership. This commit supplies the verification gate; it reports no
newly observed client asset results without the original raw input.

## Exact native Gadget reader direct-store trace (2026-10-21)

The [bounded disassembly run](https://github.com/RinoPaw/Genshin-Reverse/actions/runs/39475423384) completed against the exact SHA-256-pinned Global 7.1 executable. We traced method `GMENPOPMKAA` / method index `483590` / RVA `0x10278E50` over a **5,120-byte** code slice using the existing `tools/disassemble_rva.py`. That slice decoded **1,278** instructions; the first `ret` is at `0x1027A025` (1,145 instructions, 4,566 bytes from the method start). Some branches jump beyond this return, so its following cold paths have **not** been fully characterized.

A bounded static scan of direct `mov` stores through that first return finds **22 distinct offsets** from the same owner pointer (`r14`): **eight 1-byte offsets `0x78..0x7F`**, eight 4-byte offsets `0x68,0x6C,0x70,0x74,0x80,0x84,0x90,0x94`, and six 8-byte offsets `0x48,0x50,0x58,0x60,0x88,0x98`. The eight contiguous byte fields agree structurally with the **eight bool declarations** in native metadata owner `DCCHEHMHFGC`. The reader's store order is not declaration order; two boolean offsets (`0x7D`, `0x7E`) appear in alternative branches. That is evidence for an owner-layout candidate, **not a confirmed individual field mapping**, and not a decoded Gadget record.

All 22 offsets and their instruction RVAs are in [the static trace](7.1-chest-native-gadget-reader-static.json). Its source includes the original native executable SHA-256, run link, exact disassembler command and original disassembly JSON SHA-256. The temporary push trigger used for that run was removed; the repository's generic disassembly workflow remains manual-only.

The next work item is to correlate the declared metadata order with real IL2CPP in-memory field offsets, recover the reader's mask/encoding and loader, and decode the **verified binary Gadget table**. Do not reinterpret these bytes as `chest_puzzle`, reward tiers, Chinese `drop_tag` or loot weights. **No original 7.1 reward numbers have been established.**

## Native Gadget field-order and presence-mask gate (2026-10-21)

The exact 7.1 Gadget reader `DCCHEHMHFGC.GMENPOPMKAA`
(method 483590, RVA `0x10278E50`) has now been correlated with its
22-field metadata declaration using a bounded in-memory layout hypothesis.
Under natural 8/4/1-byte alignment, **one** candidate start (`0x48`)
matches all 22 distinct direct object-store offset/width pairs. This is a
*layout candidate*, with inherited object layout and wrapper ABI unverified;
see [layout snapshot](7.1-chest-native-gadget-layout-candidate.json)
and `scripts/correlate-7.1-gadget-reader-layout.py`.

The reader's explicit row-mask code advances the input cursor by **eight
bytes** and computes the 64-bit mask as
`(uint64_le + 0x466DB4EB) mod 2^64`. The [field-order report](7.1-chest-native-gadget-presence-bits.json)
records **22 distinct presence bits**, each exact `TEST` RVA,
its immediate value and following control-flow branch. There are 22 tested
field guards across bits 0 through 28, in native read order. A guard's branch
can select a zero/default path; the field's semantic name remains opaque.

Eight sequential metadata `bool` fields align to candidate memory
offsets `0x78..0x7F`. Each has a byte read compared with a separate
constant using `SETNE`; [the pinned boolean-byte record](7.1-chest-native-gadget-boolean-wire.json)
contains the exact comparison and store RVAs.
The three opaque tokens `NGDGAAEHPHB`, `MECPCDBEFBG` and
`OLOLLKJCHHI` map respectively to offsets `0x78`, `0x7C` and
`0x7F` **conditionally on the layout model**. They remain unnamed native
booleans; no mapping to Chest grade or interactivity is established.
