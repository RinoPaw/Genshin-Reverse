## Exact native Gadget reader direct-store trace (2026-10-21)

The [bounded disassembly run](https://github.com/RinoPaw/Genshin-Reverse/actions/runs/39475423384) completed against the exact SHA-256-pinned Global 7.1 executable. We traced method `GMENPOPMKAA` / method index `483590` / RVA `0x10278E50` over a **5,120-byte** code slice using the existing `tools/disassemble_rva.py`. That slice decoded **1,278** instructions; the first `ret` is at `0x1027A025` (1,145 instructions, 4,566 bytes from the method start). Some branches jump beyond this return, so its following cold paths have **not** been fully characterized.

A bounded static scan of direct `mov` stores through that first return finds **22 distinct offsets** from the same owner pointer (`r14`): **eight 1-byte offsets `0x78..0x7F`**, eight 4-byte offsets `0x68,0x6C,0x70,0x74,0x80,0x84,0x90,0x94`, and six 8-byte offsets `0x48,0x50,0x58,0x60,0x88,0x98`. The eight contiguous byte fields agree structurally with the **eight bool declarations** in native metadata owner `DCCHEHMHFGC`. The reader's store order is not declaration order; two boolean offsets (`0x7D`, `0x7E`) appear in alternative branches. That is evidence for an owner-layout candidate, **not a confirmed individual field mapping**, and not a decoded Gadget record.

All 22 offsets and their instruction RVAs are in [the static trace](7.1-chest-native-gadget-reader-static.json). Its source includes the original native executable SHA-256, run link, exact disassembler command and original disassembly JSON SHA-256. The temporary push trigger used for that run was removed; the repository's generic disassembly workflow remains manual-only.

The next work item is to correlate the declared metadata order with real IL2CPP in-memory field offsets, recover the reader's mask/encoding and loader, and decode the **verified binary Gadget table**. ## Definitive exact 7.1 Gadget table wire result (2026-10-21)

`a35e3f3ed04f950cb6302099d12aa71e23ece21d8fe578950347d9318f769e35`;

Three pinned **native** methods establish the real table wire path:

| Responsibility | Original IL2CPP owner / method | Method index | RVA |
| --- | --- | ---: | --- |

The original header `29cc0adc` decodes by
`(uint32_le + 0x23F5AB5E) modulo 2^32` to exactly **30,599 rows**.
Each record's inherited mask decodes by
`(uint16_le + 0x5486) modulo 2^16`, with eight native presence bits.
The old hypothesized `+0x5473` transform has been **rejected**.
The original client contains 12 actual inherited-mask combinations and
20 observed base-record widths. The parent reader decodes eight
field slots, including a chunk-XOR UTF-8 string:
`Gadget_Special_Middle_01`, `Gadget_Vehicle_Skiff` and other

preserve exact counts, field presence and source identities.

The original 2,854,884-byte payload is covered **completely**
by one 4-byte table header, **831,612 bytes of inherited row records**,
and **2,023,268 bytes of gadget-specific row records**.
All 30,599 native rows decode sequentially with unique pre-wrapper key
scalars; final offset equals EOF. The decoder no longer hunts for
`FF FF FF FF` or guesses record boundary markers.

**Critical wrapper boundary:** inherited field `0x30` reads a serialized
`uint32` plus `0x4894CEA6`, then calls native

and an XOR before storing the runtime value. The table loader
calls `0xBB15F50` to read its key. Another field `0x18`
also uses this wrapper. These two dynamic lookup tables and
the round-trip equivalence remain unverified.
The 30,599 wire scalars and native call sites are authenticated;
**the final runtime-managed object representation is not**.

## Global 7.1 runtime ID-wrapper boundary (2026-10-21)

The exact 7.1 native writer `0xBB16020` and getter
`0xBB15F50` both resolve through independent RIP-relative
instructions to the same IL2CPP static-owner pointer
**`0x57831E8`** and XOR word address **`0x578B100`**.
The writer uses byte substitution pages `0x000..0x3FF`, the getter
uses `0x400..0x7FF`; both refer to a dynamically initialized managed
table reached through static data offset `0xF560`.
The original [exact-EXE xref scan](https://github.com/RinoPaw/Genshin-Reverse/actions/runs/39532251021)
reproduced **1,073,249** candidate `MOV/LEA` RIP-relative byte
patterns to the shared static-owner pointer and **430** to the XOR
word address, showing why those globals do not identify a unique
Gadget-specific initializer. The source tool uses bounded output
samples with exact totals and original-client SHA-256 checks.
Neither target RVA has directly file-backed bytes in the pinned PE
image; reading the original EXE alone does not recover its runtime
lookup bytes or XOR value.

See the [source-pinned global report](7.1-chest-native-gadget-wrapper-global-boundary.json),
[wrapper/getter instruction evidence](7.1-chest-native-gadget-key-wrapper-evidence.json),
and `scripts/probe-7.1-gadget-wrapper-globals.py`. A
`MOV/LEA` byte-pattern scan cannot detect the writer's
`XOR [RIP+disp]` instruction or prove absence of indirect
writes. Native function boundaries and runtime initialization require
a separate investigation.

A sufficient and necessary **conditional** round-trip test
once the exact 2,048-byte lookup is acquired is:
`getter_page[i][writer_page[i][x]] == x`
for all four byte lanes and all 256 byte values. The common XOR word
then cancels if it is identical at both calls.
**No actual lookup table has been captured**, so a full round-trip
claim remains withheld.

This generic runtime wrapper is not the likely origin of server
`drop_tag` or payout tables. The next higher-value task is an original
source chain for scene gadget instances and server reward ownership;
the previously inherited `Scripts/Scene` tables remain historical
evidence only.
