# 7.1 ordinary chest rewards: source and statistical evidence

Reviewed: 2026-10-15. Scope: the **four exploration chest grades** (common, exquisite, precious, luxurious). Not Shrines of Depths, Primal Obelisks, quest-exclusive reward chests, Remarkable Chests, boss flowers, or event-specific variants.

**Finding:** we can recover a large, executable **historical server drop model**, and community sources constrain reward categories and fixed/ranged amounts. We **cannot** currently certify a complete original-client 7.1 ordinary-chest item probability distribution, particularly for post-Sumeru regions.

## Evidence classification and provenance

| Evidence | What is established | What is not established |
| --- | --- | --- |
| Scene gadget Lua + current 7.1 gadget/area resources | Entity identity, prefab/grade, explicit `chest_drop_id`, geolocation; surviving `drop_tag` strings on some old chests | Which combat/puzzle pool the original 7.1 server selects when the chest has neither a tag nor a payable drop ID |
| `RinoPaw/AstaPS:data/ChestDrop.json` (blob `789e885d37535280dc923e5c69e1aa2fc23714dd`) | Historical server-side **tag → level threshold → root drop ID** selections | That its Chinese tags were required original 7.1 semantics or that it covers newly released regions |
| `RinoPaw/AstaPS-Resource@5ff5f0b`, `Server/DropTableExcelConfigData.json` + `DropSubTableExcelConfigData.json` | Exact stored `randomType`, `weight`, `countRange`, reachable subnodes | Original **7.1** live server probabilities; see [drop-table provenance audit](7.1-drop-table-provenance.md) |
| [Genshin Impact Wiki / Chest](https://genshin-impact.fandom.com/wiki/Chest) and [Adventure EXP](https://genshin-impact.fandom.com/wiki/Adventure_EXP) | Community-observed typical chest reward amounts, item categories, exceptions, and Luna I change notes | Per-item drop weights or representative, version-pinned raw opening logs |
| [Reddit discussion of increased-reward areas](https://www.reddit.com/r/Genshin_Impact/comments/mzh98n) | Anecdotal independent observations consistent with geographical exceptions | Reliable item probability estimates, sample-size controls, 7.1 equivalence |

**Critical date check:** [the separate provenance audit](7.1-drop-table-provenance.md) confirms that the two `Server/` tables in AstaPS-Resource (13,823 main rows and 1,885 subtable rows) already appeared **unchanged in value** in an April 2026 6.5-labelled LunaGC resource set. An additional 7.0 collection expands some Dungeon tables but does not establish an up-to-date 7.1 chest export. These are **legacy-compatible configuration candidates**, not native 7.1 probabilities.

## Current native-looking server graph coverage

Read-only audit run: [RinoPaw/AstaPS-Resource, native chest source report](https://github.com/RinoPaw/AstaPS-Resource/actions/runs/38601997362), with source script [`audit_chest_native_sources.py`](https://github.com/RinoPaw/AstaPS-Resource/blob/8be655e9f2c5471248f3441166194c979f515a8e/tools/audit_chest_native_sources.py).

- 168 tagged `ChestDrop.json` source entries resolve to **96 distinct root table IDs**; all 96 exist and have nonempty `dropVec`.
- Their union reaches **612 distinct main/subtable nodes** and **198 distinct non-table terminal IDs**. A terminal ID is **not** automatically a validated inventory item; `ItemData` validation is separate.
- The 168 entries cover **Mondstadt, Liyue, Inazuma, Sumeru and event archipelago** (with Dragonspine-specific tags), but **not Fontaine, Natlan, Nod-Krai or Snezhnaya**.
- All **84** matched combat/puzzle source pairs (same tagged quality, region, level threshold) have **different recursively hashed table structures or values**. This proves nonidentical *configured graphs*, not that the final item output distributions differ by a quantified amount or that these graphs represent 7.1.
- Original `DropTableExcelConfigData` fields include `randomType`, `dropVec[].itemId`, `countRange`, `weight`, `fallToGround`. Some item IDs reference nested tables; dropping this nesting without an explicit statistical model changes results.

### Example of version mismatch

The historical `战斗低级蒙德` root `51010000` contains `itemId=102`, `countRange="10"`, `weight=10000`; its `解谜低级蒙德` counterpart `52010000` contains the same amount. The historical `战斗中级蒙德` root `51010500` contains `itemId=102`, `countRange="20"`, `weight=10000`.

In contrast, the current Wiki's Chest change log says **Luna I standardized all chest grades to 30 Adventure EXP**. The dated 7.1 source-research goal must therefore **not** promote the older 10/20 Adventure EXP rows to original 7.1 defaults. The server's own `rewards.css` may separately override Adventure EXP; that is not proof that the old drop graphs are original.

Historical Mora rows are also specific configurations (for instance `51010000` uses `itemId=202` with `240;360`), not independently verified 7.1 chest-average distributions.

## Chest instance → reward root coverage

A separate scan of four-grade chest prefabs in available `Scripts/Scene` Lua found **6,141** instances. From their authored reward fields:

| Entry state | Instances | Interpretation |
| --- | ---: | --- |
| Region/quality `drop_tag` | 4,846 | Historical server selection available; no independent 7.1 pool provenance |
| No tag; non-sentinel explicit `chest_drop_id` | 300 | Direct graph candidate; **295** point to a present nonempty server drop table, **5** do not |
| No tag; `chest_drop_id=1000100` | 27 | Present root but **empty** `dropVec`; do **not** treat as a payable reward |
| Neither tag nor useful drop ID | 968 | Cannot prove original reward pool from these fields alone |

Area reconciliation [completed separately](https://github.com/RinoPaw/AstaPS-Resource/actions/runs/38588729087): all 6,141 chest instances have a supported geography from explicit `area_id` or geolocation (Scene 1 uses the Scene 3 world polygon geography). **1,295** lack a recognized region `drop_tag`, so a tag-based region system is not complete.

**The 295 table pointers require a second gate:** a populated drop table is not proof that its contents are generic exploration loot. Explicit quest items, extraordinary chests and special handling still need class/claim-context checks.

## Community-facing reward constraints (NOT drop probabilities)

The current [Wiki chest page](https://genshin-impact.fandom.com/wiki/Chest) lists:

| Grade | Primogems | Adventure EXP | Mora | Sigils |
| --- | --- | --- | --- | --- |
| Common | 0–2, geographically selected | 30 | 257–996 | 1–3 |
| Exquisite | 2–5, geographically selected | 30 | 756–1,367 | 2–4 |
| Precious | 5–10, geographically selected | 30 | 1,433 | 3–10 |
| Luxurious | 10 for ordinary chest | 30 | unresolved in that table | 4–10 |

Exceptions: most early Mondstadt/Liyue areas use the lower Primogem tier; higher-reward subregions and nations outside those two use the higher tier. Some named special chests have unique scripted rewards (Shrines, Obelisk restoration and quests). These must be handled **before** the generic model.

The Wiki identifies possible enhancement-material, equipment and artifact rarities by grade and inventories of possible weapons/artifact sets. It does **not** provide robust per-item frequencies with sample sizes. Searches for ordinary-chest opening datasets mostly surfaced **chest-location/count surveys**, **Primogem totals**, **boss/Domain farming data**, or **gacha samples**, which must not be substituted for ordinary chest loot rates. The available statistics are therefore **constraints on an operator-authored model**, not a fully reproducible numerical distribution.

## Proposed server reward authority

1. **Explicit valid instance drop**: `chest_drop_id` with a valid nonempty table, after special/quest/dungeon classification. Use existing table execution, with CSS fixed-amount overrides applied exactly once.
2. **Known historical source only when deliberately enabled**: legacy `drop_tag` can remain an *optional compatibility input*, not a required authoritative classification nor a JSON export key. It should not silently determine the behavior of modern tagless chests.
3. **User-editable four-grade defaults**: when no authenticated source exists, choose by prefab quality and verified scene/area. Prefer one human-readable pool per grade with optional regional overrides, and explicit per-entity overrides for genuinely special cases. Use the **same** drop-table executor instead of a second random algorithm.
4. **Provenance field per rule**: `source = official-verified | historical-server | community-estimate | custom`; metadata for provenance must not be mistaken for native scene metadata. Save citations and source version for statistical estimates.
5. **Fail-closed for special chest contexts**: never award generic loot to a known scripted reward chest just because its old pointer is empty or missing. Emit diagnostics with `sceneId/groupId/configId` rather than guessing combat versus puzzle.

## Unresolved gates

- A genuinely **7.1-pinned original-game ordinary chest drop source**, especially post-Sumeru, has not been found. Client reversal alone may not recover server-only selection.
- Precise `Mora`/`sigil` distributions and probabilities for weapons/artifacts/enhancement materials are **not** established by Wiki reward ranges.
- Combat/puzzle reward equivalence must be compared at the **terminal-item probability distribution** level. Hash inequality of two graphs does not quantify their player-visible difference.
- When authoring default distributions, mark selected probabilities as **custom**. Avoid made-up percentages promoted as native.

This research changes **no AstaPS reward implementation** and does not grant chest loot during the audit.

## 7.1 GadgetExcel cross-source identity audit (2026-10-21)

To separate **what the game client calls a Chest gadget** from **which reward the server pays**, we directly compared complete `ExcelBinOutput/GadgetExcelConfigData.json` files by integer `id` (not by localized `drop_tag`):

- Independent **CN 7.1 community extraction**: `DimbreathBot/AnimeGameData@792978e5503ecfba73dcb3562ed44a0d35a2abe2`, Git blob `e6083ad777b1f427b5dbe3c8f689f3cee4475b64`.
- Current AstaPS resource copy: `RinoPaw/AstaPS-Resource@c0213668889ed05cbeb86660f424c3daf18bfacd`, Git blob `9b32db003dcc37468a3824c8de41d14b7d69cd93`.
- Both tables have **30,599** gadget definitions and **309** literal `type: "Chest"` rows; the 309 Chest IDs join **309/309**, including identical `jsonName` values (148 distinct names). For every Chest row, all **fields present in both copies** agree exactly, using lossless integer handling for hashes exceeding IEEE-754's safe integer range.
- The rows are **not byte-identical**. The CN extraction contains three extra opaque boolean keys in the Chest subset: `NGDGAAEHPHB` in **260** rows, `MECPCDBEFBG` in **61**, and `OLOLLKJCHHI` in **108**; the resource copy omits them. The resource copy explicitly sets `isInteractive: true` in **six** Chest rows where the CN extraction does not contain the key: IDs `70800641, 70800928, 70801130, 70900386, 73003003, 73011049`. This comparison cannot distinguish deliberate edits from differing exporter/default-value policies.
- **33** Chest records are field-for-field identical. Remaining differences are key presence only; **no contradictory value was found where both copies have the field**.

The client/table field `type: "Chest"` is **not the four-grade treasure chest taxonomy**. Its 309 definitions include objects named `SearchPoint` (13 rows), `SceneObj_Desert_DeshretRune` (27 rows), book-page and special-event gadgets. Conversely IDs `70210001..70210006` all have the **same** `jsonName: "SceneObj_Chest_NormalChest"`; the prefab name does not itself prove their four distinct reward grades. Any server-side ID→grade assignment must be explicitly attributed as a derived classification until an exact-client grade owner is found.

### Provenance and reward gates

1. This is a **cross-source, cross-region consistency check**, **not an authenticated original Global 7.1 asset extraction**. Neither Git blob SHA establishes the original packaged client asset or the extractor's lossless semantics. The unrecognized boolean keys must remain opaque until verified by native metadata/deserialization.
2. No observed `GadgetExcel` fields are a verified ordinary chest **reward probability table**. In particular, identical gadget identities do not validate the historical `ChestDrop.json` tag→root mapping, or any `Server/DropTableExcelConfigData.json` weights.
3. On the current AstaPS Loot branch `feat/nested-yaml-loot-71`, `ChestTypeResolver.fromExploreKind("chest_puzzle")` produces a server-derived `normal` type, while its grade is unresolved. `NodKraiExploreSpawnHelper.dropTagForKind` and `SnezhnayaExploreSpawnHelper.dropTagForKind` **synthesize** Chinese `drop_tag` values for imported map points. Those generated tags must never be recorded as source-authored scene Lua or an original client category.
4. For any payable ordinary chest, require a **separate, source-proven** placed instance/grade and exclusion of quest, event, puzzle-only and other special Chest gadgets. Keep source fields, derived classification and operator-designed default rewards separately attributed. Failure to classify is an unresolved case, not permission to assign common/exquisite rewards.

**Reproduction:** fetch the two pinned Git blobs as raw text, parse integers without floating-point conversion, index the `type == "Chest"` entries by `id`, assert no duplicate IDs, compare each union of field names using explicit *missing* sentinels, and separately report (a) changed values where both fields exist and (b) one-sided keys. Do not stringify the original hashes through JavaScript `Number` before comparing.

**Next original-data gate:** obtain the exact **Global 7.1 client asset bundle** and its acquisition manifest; trace `GadgetExcelConfigData` load and unknown field semantics through the pinned executable/metadata. Treat the independent CN dump as a comparison vector until that chain is complete. The presence/absence of ordinary-chest server-weight tables remains a separate question.
