# Original Global 7.1: who owns world-chest placement?

Status: **UNRESOLVED**. Source scope: exact Global 7.1 original Windows client only. Question: does the client ship complete world-chest coordinates/scene-instance `level`, or does it receive these from an official server?

## What is now source-verified

- The exact official compressed Sophon manifest, original design asset index, original WorldArea-containing Unity bundle `00/24230448.blk`, and scene 3 WorldArea raw object have independent hashes; see [the native index/export coverage evidence](7.1-original-worldarea-design-index-export-coverage.json).
- The original design index maps **167,673** distinct 40-bit asset hash rows to this block. Original Raw export produces exactly **167,673** hashed `MiHoYoBinData` files (**415,672,040** bytes). All exported 32-bit filename stems correspond to an index row mapped to the same block: **167,667** unique-name matches and **6** 32-bit-name collisions with another index row. The original 40-bit identities distinguish these six cases; their 32-bit exported filenames cannot independently disambiguate the rows.
- Thirteen independently verified original WorldArea assets belong to the block. WorldArea describes area geometry; this does not identify chest placement.
- Original `GadgetExcelConfigData` contains 30,599 native decoded Gadget rows including 20 original chest-prefixed literal names. Direct little-endian u32 Gadget ID byte scanning fails its **known-positive original GadgetExcel source** (0/20 IDs detected despite all 20 decoded rows), and likewise yields zero in WorldArea block exports. The scan is **not a valid absence test** for original scene instances.

## 7.1 original Scene/Point source prefixes and native array count-reader candidate (2026-10-22)

[Exact Global 7.1 native verification run 39734845897](https://github.com/RinoPaw/Genshin-Reverse/actions/runs/39734845897) compared the original-client source-authenticated 32-byte prefixes of all 13 `Scene/Point` assets against the *exact original* Windows x64 executable's aligned instruction immediates. A deliberately loose `floor(payloadBytes/2)` physical bound on possible 32-bit decoded array counts, applied to offset positions 0–8 and XOR/ADD, yielded 44 numerical candidates: 22 XOR from prefix byte offset 3 and 22 ADD from offset 6. **Exactly one** constant survived matching against a 4-byte aligned immediate in a decoded original native instruction: `0xC14B813C`.

The source-original reader `NLDEPJEOJGC.GMENPOPMKAA` (metadata method index **514423**, RVA `0xAD23000`; 1,568-byte complete bounded method SHA-256 `6319613278adf382bf7ce513d1d875ef98b318d5f5f3bc9c423b72caebd7c0ad`) contains a verified four-byte stream read and array length transform: `0xAD23066 mov ebx,0xC14B813C` followed by `0xAD2306B xor ebx,[rax+rdx+0x20]`, with source cursor advancement and a subsequent element-count-controlled loop. Thus the **native generic array count read and XOR operation are confirmed**.

Applying that native transform to little-endian source words at **hypothetical input offset +3** yields values `1727,28,28,20,14,60,19,24,18,25,56,26,1` across the 13 independently verified Scene Point assets. Their physical source lengths do not falsify the hypothesis. Crucially, **the caller that initializes the Scene/Point stream cursor at offset +3, invokes this native method and consumes every Scene Point row is still unverified**. The current values are candidate counts, not certified game scene-point numbers, entity positions, chest counts or group/Gadget instances. [Machine-readable source trace](../world/7.1-original-scene-point-native-xor-reader-evidence.json) retains the exact native instruction and provenance evidence. ## Original 7.1 Scene Point-compatible nested array reader source call chain (2026-10-22)

[Original Global 7.1 SHA-verified source run 39737316657](https://github.com/RinoPaw/Genshin-Reverse/actions/runs/39737316657) found **one** exact, instruction-aligned native direct E8 call to `NLDEPJEOJGC.GMENPOPMKAA` (RVA `0xAD23000`; verified XOR-count reader) from `IJNOFJEOMBD.GMENPOPMKAA` (RVA `0xEE66B20`, original method index `171707`). The original outer method spans **864 native bytes** and **203 decoded instructions** (SHA-256 `e27dc0d3a924a74963b34e8d8ff64d17ab3fe472b77dcc42b4cbe3c704a6e61a`). Its native code reads a 16-bit mask value and adds `0xF077` modulo 2^16; it conditionally calls the nested XOR-count array reader at `0xEE66BF1` using address `r14 + 0x30`, gated by native mask bit `0x4000`.

**All 13 SHA-authenticated original Scene/Point resource prefixes** pass this outer 16-bit source-mask interpretation: the computed mask contains both `0x8000` and `0x4000`, and the third source byte is `0xCB` for every scene. The native `0x8000` path calls `CCPCOHEPGHC.GMENPOPMKAA` (RVA `0x12498FE0`, original method index `173227`). Its independently file-backed and hashed instruction sequence reads an **initial byte**, increments the binary input cursor and stores the new cursor. **The remainder of that nested reader's branches is not fully resolved for byte `0xCB`**, and may consume additional data. Thus the next native array count's predicted source offset `+3` remains **unproven**, despite the compelling cross-scene structural match.

The original compiled parser provides a real outer-to-inner call relationship. The direct relationship between the original *resource path* `Data/_BinOutput/Scene/Point/scene*_point` and the outer parser's runtime input has **not** been authenticated by a loader/path lookup or full source byte-consumption check. Original chest Gadget config IDs, instance positions, `level`, server-exclusive placement storage and reward policy consequently remain **unresolved**.
